# HymV2 项目目的与要求

## 1. 项目定位

HymV2 的核心目的不是做一个通用 UI 点击器，也不是追求“脚本没有报错”。

项目需要在无人值守的情况下，自动完成多个 App 中能够获得奖励的日常任务，尽可能确认奖励结果，排除弹窗、广告落地页等干扰，并记录足够的执行证据。后续只需要查看服务端数据，就能知道每台设备、每个 App、每个任务是否完成以及失败在什么位置。

判断功能价值时按以下顺序取舍：

1. 奖励任务是否真实完成，奖励是否到账或有可信的完成证据。
2. 当前异常是否会阻断同一 App 的后续任务，或阻断其他 App。
3. 无人值守失败后，是否留下足够且易分析的现场信息。
4. 是否高效，不能为了少量异常增加大量检测、等待和复杂逻辑。
5. 是否便于增加新 App、新任务类型、新页面分支和新设备后端。

## 2. 当前业务范围

当前需要覆盖四个奖励类 App，并允许继续扩展：

| App | 内容类型 | 当前主要任务 |
| --- | --- | --- |
| 快手极速版 | 短视频 | 浏览、概率互动、签到、时段奖励、激励广告、余额记录 |
| 抖音极速版 | 短视频 | 浏览、概率互动、签到、时段奖励、激励广告、余额记录 |
| 趣头条 | 新闻/图文 | 随机打开文章或视频、阅读到底部、评论区浏览、签到、奖励、余额记录 |
| 喜马拉雅极速版 | 听书/音频 | 恢复播放、维持播放会话、有限状态确认、奖励相关扩展 |

微信是独立的可选维护模块，不属于奖励任务主流程。目前只允许查看朋友圈、查看零钱等只读操作，不自动聊天、不点赞、不评论。个人微信的安全边界必须独立配置，不能因为奖励 App 的通用逻辑而扩大操作范围。

`network`、MQTT、SSE 只是临时测试，不纳入本轮架构和业务判断。

## 3. 明确不自动执行的操作

以下操作默认需要人工确认，不能放进日常无人值守流程：

- 首次隐私协议、用户协议等授权。
- 微信或其他第三方登录的最终授权确认。
- 提现、支付、转账、兑换等资金操作。
- 发送微信消息、朋友圈点赞或评论。
- 无法确认后果的活动入口和营销页面。

登录状态需要有前置检查和扩展接口，但当前登录前流程由用户手工完成。日常任务发现未登录时，应明确记录并跳过相关任务，不能反复点击授权页面。

## 4. 总体执行规则

### 4.1 每日任务编排

- 签到和内容浏览的先后顺序随机，避免每天固定顺序。
- 余额记录随机插入当天流程，但同一 App 每天保证成功记录一次即可。
- 签到等每日一次任务必须持久化状态，已完成后当天不重复执行。
- 每轮开始时冻结业务日期；长流程跨过午夜后仍写入本轮日期，下一轮才切换到新一天。
- App 中的任务和页面流程不假定固定。相同任务可以存在多个入口、多个中间阶段和多个成功页面。
- 一个步骤失败后，优先返回首页或任务页重新进入；达到有限次数仍失败时，记录结果并继续其他任务。
- 单个 App 失败不能阻断其他 App；单个广告失败也不能阻断签到、余额和内容任务。

### 4.2 结果判定

统一使用以下结果语义：

- `success`：核心业务结果已确认，例如奖励到账、明确完成提示或回到可信结束页。
- `already_done`：根据当天持久化记录确认已经完成。
- `skipped`：配置跳过、当前无可领取任务或不满足安全前置条件。
- `partial`：完成了部分价值，但附加奖励或收尾状态无法完全确认。
- `failure`：核心任务没有完成；允许工作流恢复后继续执行。

“成功点击按钮”“页面没有报错”不能单独作为任务成功。广告通过恢复动作退出但没有确认奖励时，也不能计入已完成数量。

### 4.3 随机行为

- 内容数量、停留时间、滑动距离、点击位置和操作顺序允许随机。
- 点赞、评论区浏览、主页浏览、作品浏览、关注均按独立概率执行。
- 所有概率、数量和等待范围都应由配置控制，并支持全局、设备和 App 分层覆盖。
- 所有随机数量和时长范围均支持最小值、中心值、最大值和标准差，统一采用有界正态分布；未配置中心值时使用范围中点。
- 用户可感知的停留、滑动、内容数量和任务次数使用上述随机模型；定位超时、失败重试预算和奖励保底计时属于正确性边界，不为追求随机而扰动。
- `timing_scale` 控制普通等待快慢，`jitter_ratio` 控制随机浮动程度。
- 奖励兜底等待使用独立倍率；可靠完成信号已经命中时，可以结束兜底计时，但退出前仍需随机停留一小段时间。
- 随机行为用于避免机械化固定路径，但不承诺绕过平台检测，也不能以牺牲奖励到账为代价。

等待类逻辑遵循“结果优先、兜底其次”：存在可靠结果信号时低频检查，命中后再加入短暂的人类操作停留；无法可靠判断或超时未命中时才使用固定兜底。不能为了少量异常增加高频 UI、截图或 OCR 检测。

### 4.4 随机插空与任务续跑

允许在一个 App 尚未完成全部任务时，低概率临时切换到另一个 App，或返回桌面随机等待几十秒，再继续未完成的任务。这种插空由统一调度器负责，App 插件不能自行启动其他 App。

插空只能发生在明确的安全中断点：

- 一条视频或一篇文章处理完成后。
- 一个独立任务步骤完成并已经记录结果后。
- 页面已经回到可重新识别的首页或任务页时。

以下阶段默认不可中断：

- 激励广告已经开始但本轮奖励还没有确认。
- 签到、领取奖励等提交按钮已点击，正在等待结果。
- 弹窗正在执行“继续领取”或最终退出的连续动作。
- 任何中断后可能导致奖励丢失或重复提交的关键区间。

每次中断需要保存任务游标，包括原 App、工作流、步骤、已完成数量和恢复策略。再次切回时先确认当前页面：能够安全续跑的步骤从游标继续；页面状态已经失效的步骤从该任务入口重新进入；每日一次任务依赖持久化检查点避免重复提交。

支持两类随机插空：

1. App 插空：从当前安全点切到另一个尚有待办任务的 App，执行一个有界任务切片，之后由调度器继续选择待办任务。
2. 桌面插空：按 Home 回到桌面，在配置的最短和最长时间之间随机等待，再恢复待办任务。

插空配置至少应包含：是否启用、触发概率、App 切换与桌面等待的概率、桌面等待秒数范围、两次中断的最短间隔、单轮最大中断次数。默认不允许中断嵌套，避免多个 App 互相切换形成无限调度。

检测中断机会只在安全点做一次轻量概率判断，不增加后台轮询、截图或 OCR。暂停 App 时默认不强制停止进程。音频是否允许在后台继续累计任务时间，需要按 App 的真实奖励规则单独声明。

当前执行器已改为单步骤切片调度。视频、新闻和音频会话会在安全点保存步骤内进度，切换后继续剩余内容；工作流游标同时写入本地状态，供日志分析和后续服务端查看。当前持久化游标不用于进程重启后的任意页面盲续：进程重启仍从任务入口重新识别页面，并依靠每日动作检查点避免重复领取。

## 5. 内容任务要求

### 5.1 短视频

- 每轮随机浏览若干内容，每条内容随机停留。
- 普通、长内容、明确广告、疑似广告和无法分类内容分别处理。
- 内部分类必须使用稳定机器码，中文名称只用于日志展示，不能通过修改文案改变策略分支。
- 普通视频只允许低概率快速划过；大多数内容应有合理最低观看时间，并随机选择一部分尝试完整观看。
- 能读取可靠进度或结束标记时以结果为准；拿不到真实时长时使用明确标注的较长等待兜底，不能把兜底误报为确认看完。
- 点赞、评论区浏览、主页、作品、关注都是概率动作，不是每条必做。
- 未可靠分类的内容不执行可能产生外部影响的互动；可按 App 的真实广告特征配置为疑似广告并快速划走。
- 内容分类耗时应计入停留时间，避免识别完成后再重复等待。

### 5.2 信息流广告

- 尽量在合理时间内识别广告，优先使用稳定结构、ID、文案和局部 OCR。
- 已确认广告后不点赞、不评论、不关注，避免错误互动。
- 视频流存在但关键分类标记均未命中时，可按 App 配置为疑似广告快速划走；日志必须区分明确命中和弱判定。
- 视觉广告证据可以覆盖普通内容结构标记；新广告特征应追加到对应 App 规格，不写进公共视频循环。
- 广告内容允许短暂停留，不能因为慢识别导致整条广告播放结束后才做出判断。
- 广告判定失败不能阻断后续内容，连续多条无法识别时再执行有限恢复。

### 5.3 新闻/图文

- 从列表中随机选择文章，不能总点固定位置或固定标题。
- 阅读时允许随机滚动，并能按概率浏览评论区、点赞等已配置动作。
- “读到底部”等有任务要求的动作需要完成，但某篇详情无效时应跳过并继续下一篇。

### 5.4 听书/音频

- 音频不是逐条快速滑动模型，应按播放会话处理。
- 优先恢复可播放内容，保持一段配置时长，仅做低频状态确认。
- 播放页变化或偶发状态不应导致频繁重启 App。

## 6. 激励广告要求

激励广告的目标是拿到奖励，不是尽快关闭广告。

1. 识别到广告播放页后，优先低频检查经过真机确认的奖励完成信号，不高频解析 UI。
2. 命中完成信号后，在配置范围内按正态分布随机停留，再触发退出；当前建议 `1~10` 秒、中心值 `5` 秒。
3. 没有可靠完成信号或始终未命中时，完整等待配置的奖励兜底时间；兜底不能因随机浮动提前结束。
4. 如果弹窗明确表示“继续看下一条仍可获得奖励”，允许随机追加观看有限轮数。
5. 快手当前暂定每次随机追加 `0~2` 轮，可通过 `ad_extra_rounds_min/max` 调整。
6. 只有在已确认的奖励弹窗上下文中，才能点击“领取奖励”等续看按钮；相同文案出现在普通页面时不能触发续播。
7. 达到追加上限后关闭挽留弹窗，回到任务页并确认广告流程结束。
8. 广告中套广告、落地页或挽留弹窗都必须有次数上限，不能无限循环。
9. 广告失败时允许有限返回和关闭动作，最终恢复首页或任务页，不影响其他流程。

快手当前已验证的退出分支包括：

- 完整播放后按返回键进入奖励挽留弹窗。
- 弹窗可能显示“继续观看/换一个广告”，也可能显示“再看1个/领取奖励”。
- 奖励弹窗右上角的叉可以退出并回到任务中心。
- “领取奖励”只有在上述弹窗已经命中时才代表追加一轮，不能作为全局下一广告标记。

## 7. 定位与性能原则

定位优先级不是固定要求所有 App 使用同一种技术，而是按成本和可靠性组合：

1. 稳定资源 ID、文本、描述和页面 Activity。
2. UI 树结构、节点关系和页面组合标记。
3. 局部图片匹配或局部 OCR。
4. 已实测稳定的布局位置。
5. 绝对坐标只作为最后兜底。

OCR 不应每次全屏执行。只有 UI 树无法暴露目标、文本由图片渲染或需要识别金额时才启用，并限制截图尺寸和识别区域。一次观察结果应尽量复用，不能为同一步骤反复导出 UI 树、截图和 OCR。

Airtest/Poco 只是当前设备后端，不允许渗透到业务流程。上层只依赖统一的观察、定位、点击、滑动、按键和输入接口。以后换成 Android 无障碍、自研设备服务或其他后端时，App 任务语义和状态机应能继续使用或直接转译。

平衡原则：可以接受少量偶发异常，不为了约 10% 的异常增加约 50% 的代码量或运行损耗。只有高频、会丢奖励、会无限循环或会阻断后续任务的问题，才值得加入常驻检测。

## 8. App 扩展要求

每个 App 拥有独立的规格或插件文件，文件内需要用简洁中文注释说明：

- App 会执行哪些任务，任务顺序如何决定。
- 每个任务的入口、页面标记、成功标记和退出标记。
- 每日一次、次数限制和概率限制。
- 当前已知的动态分支、弹窗和真实场景结论。
- 新 ID、新文案或新布局应该追加到哪个目标中。

通用框架只负责编排、状态、恢复、日志和设备能力，不包含某个 App 的具体文案或坐标。新增 App 时，应尽量只新增 App 规格、特有任务处理器和必要资源，而不是修改公共调度器。

新增一种内容类型时，通过内容策略接口注册；新增一种底层实现时，通过设备、定位和视觉接口接入。两者不能互相依赖。

## 9. 多设备要求

- 每台设备拥有独立会话、状态命名空间、日志和诊断产物目录。
- 同一设备同一时间只能有一个工作进程持有租约，避免重复点击。
- 设备断线时有限重连，USB 正常结束会话不能主动断开 ADB transport。
- 一个设备异常不影响其他设备继续运行。
- 配置支持设备级和 App 级覆盖，不能通过复制业务代码适配不同设备。

## 10. 日志、诊断与上报

日志使用中文可读内容，同时保留稳定事件码用于筛选。关键事件至少包含：

- 设备连接、重连和关闭。
- App、工作流和步骤的开始与结束。
- 任务入口、动态阶段、成功证据和恢复动作。
- 内容序号、分类和是否执行互动。
- 每一轮奖励广告的等待开始、等待结束、追加计划、退出和最终结果。
- 随机插空的触发原因、原任务游标、目标 App 或桌面等待时间、恢复结果。
- 定位降级成功、关键目标未命中和执行异常。

每条结构化日志应带设备、App、轮次、App 运行、步骤运行等链路 ID，方便按一次真实执行完整还原。日志不能打印大量无价值 UI 节点，也不能记录聊天正文、好友名等敏感内容。

“卡住”指业务步骤多次没有推进，不是进程卡死。偶发一次不立即保存完整现场；同一任务、同一失败原因连续达到配置阈值后，再保存：

- 当前截图。
- 当前 Activity 和包名。
- 当前 UI 树。
- 最近的定位尝试和命中策略。
- 工作流、步骤、配置摘要和失败原因。

日志、结果和产物先保存到本地。上层预留统一报告接口，后续可以将同一数据上传服务端，业务插件不直接调用网络接口。

## 11. 开发与验证方式

- 优先理解和保留已经真机跑通的旧逻辑，再逐步替换实现。
- 不根据常见 App 经验直接假定真实流程；页面分支以真机观察和日志为准。
- 明确缺陷可以小步修复；涉及奖励规则、次数限制或外部影响的歧义，先记录并让用户确认。
- 每次只修改一个可验证问题，先跑自动化测试，再做单 App 真机验证。
- 快速框架验证和完整奖励验证分开，避免每次改动都重复执行所有长流程。
- 新流程允许通过人工逐步操作采集。每一步至少记录人工操作说明、操作前后 Activity、UI 树、截图和稳定标记差异，产物可直接用于补充 App 规格。
- 真机验证必须检查日志结果、页面结果和设备连接，不能只看命令退出码。
- 架构稳定的标准不是一次跑通，而是四类 App 在多次真实运行和页面变化后仍能有限恢复并留下证据。

## 12. 验收标准

一个 App 的日常流程达到可用状态，需要同时满足：

1. 能从其他 App 或桌面可靠启动并进入目标页面。
2. 已完成的每日一次任务不会重复执行。
3. 主要奖励任务有明确完成或未完成结果，不误报成功。
4. 内容任务数量、时长和概率动作受配置控制。
5. 广告和弹窗不会导致无限循环，也不会提前退出而丢奖励。
6. 单步骤失败后能继续其他任务和其他 App。
7. 重复失败达到阈值后有截图、UI 树和结构化日志可供分析。
8. 关闭运行后设备仍在线，可继续执行下一轮。
9. App 文件中的流程、限制和匹配标记足够清楚，用户可以自行追加新分支。
10. 启用随机插空后，只在安全点切换；恢复后不丢奖励、不重复每日任务，也不会无限嵌套。

## 13. 待用户重点确认

以下内容是根据当前对话和真机结果整理的暂定结论：

1. 快手奖励广告每次允许随机追加 `0~2` 轮；其他 App 只有真机确认存在奖励续看入口后才启用。
2. 信息流中的普通广告目前只停留、不互动。是否要对已确认广告低概率进入广告主页，需要单独确认收益和风险后再开启。
3. 微信继续作为独立只读维护模块，默认不参与奖励 App 的每日调度。
4. 登录、协议、提现和第三方授权继续保持人工处理，不作为当前自动化完整率的失败项。
5. “奖励已完成”优先要求到账提示或可信结束页；只有平台确实不提供完成信号时，才允许使用“完整计时并成功返回任务页”作为替代证据。
6. 随机插空仅在安全点启用；当前默认安全点触发概率为 `0.08`，触发后返回桌面的概率为 `0.3`，桌面停留 `20~60` 秒，两次插空至少间隔 `120` 秒，单轮最多 `2` 次，均可配置。
